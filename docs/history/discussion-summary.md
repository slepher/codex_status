# Codex 余量显示器：讨论总结

## 1. 项目目标

本项目计划使用带电子墨水屏的 ESP32-S3 开发板，制作一个桌面设备，用来显示 Codex 的用量、剩余额度和重置时间。

这里的“在板上开发 Codex”并不是让 ESP32 运行 Codex 模型或完整客户端，而是让设备承担以下工作：

1. 连接 Wi-Fi。
2. 获取 Codex 用量数据。
3. 解析精简后的数据。
4. 在电子墨水屏上显示余量和状态。
5. 定时刷新，并在空闲时进入低功耗状态。

## 2. 已选择的硬件

讨论中选择的是 Waveshare ESP32-S3-ePaper-1.54G。按照此前会话中记录的信息，这块板具有：

- ESP32-S3-PICO-1-N8R8；
- 双核处理器，最高 240 MHz；
- 512 KB 片内 SRAM；
- 8 MB PSRAM；
- 8 MB Flash；
- 2.4 GHz Wi-Fi 和 BLE；
- 1.54 英寸、200 × 200 四色电子墨水屏；
- RTC、温湿度传感器、TF 卡、音频和电池管理等板载功能。

这些硬件信息是对既有讨论的归纳，本总结没有重新核验产品页面。

## 3. 通用的 ESP32 开发方式

ESP32 应用通常不需要从寄存器或底层协议开始开发，也不必默认 fork 一个完整项目后大规模修改。更常见的方式是：

```text
选择应用框架
    ↓
创建空项目或官方模板
    ↓
引入板级驱动和第三方组件
    ↓
编写自己的业务逻辑
    ↓
编译、烧录和测试固件
```

本项目可以复用微雪官方示例中的板级配置和屏幕驱动，但项目主体仍然可以保持为独立工程。

## 4. 框架与工具的分工

### ESP-IDF

ESP-IDF 是 Espressif 官方开发框架，提供 FreeRTOS、Wi-Fi、TCP/IP、TLS、HTTP、NVS、OTA、Deep Sleep，以及 SPI、I2C、UART、GPIO 等基础能力。

使用 ESP-IDF 时，不需要自行实现网络协议、实时操作系统或 Flash 管理，主要编写设备业务逻辑。它适合需要长期维护、精细控制和正式产品化的版本。

### Arduino-ESP32

Arduino-ESP32 建立在 ESP-IDF 之上，提供更简洁的 C++ API。对于本项目涉及的 Wi-Fi、HTTP、JSON、电子墨水屏、按钮和定时休眠等功能，Arduino 已经足够。

讨论中的倾向是：第一版使用 Arduino/C++ 快速完成，后续只有在确有需要时再转向纯 ESP-IDF。

### PlatformIO

PlatformIO 不是运行在板子上的应用框架，而是开发电脑上的工程和依赖管理工具。它负责：

- 管理开发板、编译器和框架；
- 下载和锁定依赖；
- 编译、链接、烧录和串口监控；
- 组织不同构建环境。

PlatformIO 底层既可以选择 Arduino，也可以选择 ESP-IDF。

### 第三方库和官方示例

项目可以使用现成组件完成 JSON 解析、电子墨水屏驱动、二维码、文件系统等功能。微雪官方示例的主要价值是提供可靠的引脚定义、初始化顺序和板级驱动参考，而不是作为必须长期 fork 的完整应用。

## 5. 关于 npm 和板端性能的澄清

ESP32 本身不会运行 npm、Node.js 或 `node_modules`。PlatformIO、ESP-IDF Component Manager，以及可能使用的 npm，都是开发电脑上的构建工具。

最终烧录到设备中的内容是：

```text
机器码
+ 被实际使用并链接进固件的库代码
+ 必要的静态资源
```

开发环境和依赖源码即使很大，也不代表固件会同样大。链接器通常会排除未使用的代码。

只有当项目包含设备配置网页时，才可能在电脑上使用 npm 构建 React、Vue 或其他前端，再把生成的 HTML、JavaScript 和 CSS 静态文件压缩后放进 Flash。npm 仍然不会在 ESP32 上运行。

## 6. 内存和存储分析

本项目真正需要关注的是固件大小与运行时内存峰值，而不是开发电脑上安装了多少依赖。

主要资源包括：

- Flash：存放固件、分区和静态资源；
- SRAM：保存任务栈、网络状态和高频运行数据；
- PSRAM：可用于较大的缓冲区、JSON、图片和字体；
- Heap 峰值：HTTPS/TLS 握手、HTTP 响应和 JSON 解析时最值得关注。

200 × 200 屏幕所需的帧缓冲很小：

```text
黑白 1 bit：200 × 200 ÷ 8 ≈ 5 KB
四色 2 bit：200 × 200 × 2 ÷ 8 ≈ 10 KB
```

因此，屏幕帧缓冲不是这个项目的主要压力。HTTPS/TLS 的瞬时内存需求、字体资源和 Web 配置页更值得控制。按照讨论中的板卡配置，8 MB PSRAM 和 8 MB Flash 对第一版功能较为宽裕。

## 7. 设备的软件职责

板端应用可以划分为以下模块：

```text

```

## 8. 用量数据链路

设备最终需要获得类似下面的精简数据：

```json
{
  "used_percent": 31,
  "window_minutes": 300,
  "resets_at": 1788955200,
  "daily_tokens": 12345
}
```

此前讨论过两种方向：

### 方向 A：ESP32 直接认证和请求

ESP32 自己完成登录、Token 保存与刷新，并直接请求用量数据。优点是设备可以独立工作；缺点是认证流程、凭据安全和后续兼容维护更复杂。

### 方向 B：通过桥接服务获取数据

由电脑、NAS 或树莓派负责账户认证与数据读取，ESP32 只从局域网服务获取精简 JSON。

```text
Codex 账户
    ↓
电脑 / NAS / 树莓派上的桥接服务
    ↓
局域网 HTTP(S) 或 MQTT
    ↓
ESP32-S3 墨水屏
```

这一方向能简化板端程序，也能减少在嵌入式设备上直接保存账户凭据的风险。最终采用哪一种方式，属于后续设计决策；本总结不继续调查或替项目作出新的技术结论。

## 9. 第一版建议范围

最小可用版本可以只包含：

1. 正确初始化四色电子墨水屏。
2. 通过配置页面或预设配置连接 Wi-Fi。
3. 获取一份固定格式的用量 JSON。
4. 显示已用比例、剩余比例和重置时间。
5. 显示网络、同步失败和最后更新时间。
6. 请求失败时保留上一次成功数据。
7. 定时唤醒、刷新屏幕并进入休眠。

建议第一版暂不加入 TF 卡、音频、多 Provider、复杂动画或大量历史数据，以减少故障点。

## 10. 可选的后续能力

完成核心闭环后，可以逐步考虑：

- 多个额度窗口；
- 每日或每周 Token 趋势；
- 多账户和多 Provider；
- HTTP/SOCKS5 代理；
- OTA 固件升级；
- 二维码配网或登录提示；
- 电池电量、时间和温湿度；
- 使用 TF 卡保存历史、日志、字体或图标；
- 更完整的 Web 配置与诊断页面。

## 11. 当前结论

这个项目适合采用“独立应用工程 + 官方板级示例/驱动 + 成熟组件”的开发方式，不需要从底层开始，也不需要 fork 一个完整 Dashboard 后魔改。

第一版较合适的组合是：

```text
PlatformIO
    + Arduino-ESP32
    + 微雪官方板级与屏幕驱动
    + JSON / HTTP 等成熟组件
```

板卡的内存和存储不是主要障碍。项目真正需要优先明确的是用量数据来源、认证边界、凭据保存方式，以及屏幕上的核心信息层级。
