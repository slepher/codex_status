# AP01 双屏核对与旋钮确认绑定方案

2026-10-14，C9。状态：具体设计，未实现、未部署。用户选择通过Wi-Fi发起请求，在Bridge与AP01显示相同4位数字，按AP01旋钮确认；目的为避免误绑定、误操作，首版允许固定显示码，不要求严格加密。此决定替代AP01此前的BLE/SMP绑定路线，不改变Note4既有BLE授权。

## 1. 三种状态各司其职

| 状态 | 作用 | 生命周期 |
|---|---|---|
| binding | 这台AP01记住哪些Bridge | 持久、多对多；闲置、断网、重启均不删除 |
| owner | 当前哪个Bridge占用这台AP01 | 一个有效owner；沿用显式claim和租约 |
| pairing | 哪个新请求正在等待旋钮确认 | 最多一个，120秒；取消、超时、重启即失效 |

确认绑定只增加binding，不隐式创建owner，不发布Bundle、不启动OTA。Bridge收到持久化成功后，继续调用现有显式claim入口；界面分别显示“已绑定”和“已连接/被其他Bridge占用”。一台Bridge可记住多台AP01；一台AP01初版最多记住8个Bridge，沿用当前端点表的条数上限，按实际数量分配，不预留8份空记录。容量满明确拒绝，不自动淘汰旧绑定。

## 2. 固定数字与首次操作

每个Bridge实例首次使用时生成并保存一个`0000–9999`四位显示码，允许开发阶段预设，例如`4827`。重启、断线重连以及匹配另一台设备均不必更换。它仅供人眼核对，不是密码、token、设备主键或绑定记录主键。

绑定主键是完整`device_wifi_mac + bridge_id`。数字可能重复，所以两端还显示Bridge名称、Bridge身份短尾和AP01 MAC短尾，协议始终比较完整身份。两个Bridge出现同码不会合并记录，也不会互相续约。

首次流程：

1. 米家完成AP01配网。Bridge通过已知IP/UDP发现或手动IP读取最小身份及能力；完整MAC与预期不符立即终止。首版不依赖mDNS或蓝牙发现。
2. 用户在Bridge选择这台AP01，点击“绑定”。Bridge先持久保存本次请求ID和候选绑定凭据，再通过Wi-Fi提交；普通扫描/后台刷新不发起匹配。
3. AP01检查owner、OTA维护状态、容量、身份及是否已有待确认请求。接受后把请求投递原厂UI线程；只有UI确认该请求已显示，Bridge才提示“请核对设备上的数字并按旋钮”。
4. 两屏显示`4827`及身份提示。AP01收到显示完成后的新一次旋钮按下/释放，确认当前请求。原页面已按住的按钮、遗留点击、连击和网络请求均不能代替这个事件。旋钮转动可选“取消”；超时自动关闭。
5. 在同一个仲裁区中复核请求ID、UI代次、截止时间及owner；符合条件才原子保存binding并读回验证。存储失败显示“未保存”，不报绑定成功。
6. Bridge查询原事务，确认完整MAC、bridge_id和绑定状态后将本地候选凭据转为正式凭据，再显式claim。后续连接直接使用保存的凭据，不再显示数字。

拟定界面文案：

```text
Bridge                             AP01
绑定 AP01 · 210B                    与 Slepher Mac 绑定？
核对数字：4827                     4827
请在设备上按旋钮确认                Bridge · 8C2A  / 设备 · 210B
[取消]                             按旋钮确认 · 转动可取消 · 118秒
```

## 3. 活跃占用与空闲重新匹配

默认复用当前值：owner租约300秒，Bridge每60秒显式续约。配对等待120秒。这里的“空闲”指**没有有效owner**；图片没变化、没有新数据不等于空闲，只要Bridge仍成功续约就继续占用。有效租约本身是唯一闲置闸门，不另造一套“最后收包时间”计时器。

当前`src/owner_store.cpp`中，业务请求只更新匹配owner的`lastSeen`，只有显式claim/renew延长租约；AP01保持这个语义。读状态、无效请求、新Bridge的绑定请求不能续租。网络恢复后已经绑定的Bridge可自动claim，无需重新人工确认。

| 到达的请求 / 当前情况 | 设备行为 |
|---|---|
| 有效绑定凭据的重复绑定请求 | 返回`already_bound`，不弹码、不重写记录；其他owner存在时后续claim仍返回占用 |
| 新Bridge请求，owner有效 | `409 occupied`，不遮挡当前画面，返回剩余租约时间 |
| owner到期且无OTA维护事务 | 接受一个显式新请求并显示数字 |
| 相同待确认请求重传 | 返回原状态和原截止时间，不重绘、不延长等待 |
| 不同请求到达，已有待确认请求 | `409 pairing_busy`，不替换屏幕上的数字，不排队自动弹出 |
| 已绑定Bridge在待确认期间成功claim | 合法claim优先，取消待确认请求并恢复画面；原请求得到`owner_changed` |
| OTA维护事务进行中 | `409 maintenance_busy`，不进入匹配；独立于owner过期判断 |
| 名额满 | `409 binding_capacity`，提示在设备上移除不用的绑定 |

Bridge收到忙状态后结束本次发起，显示原因与重试入口，不每秒自动提交新请求。查询待确认事务可以每秒一次，但不能创建新请求或延长等待。用户想增加另一台Bridge时，让当前Bridge停止对该设备续约（退出或在该设备上暂停自动连接），最多等待当前租约剩余时间后再点绑定；本方案不新增force抢占或普通release旁路。

并发claim继续采用“设备先处理成功者取得owner”；其余已绑定Bridge得到409。若绑定成功后另一个已绑定Bridge先claim，界面显示“已绑定，设备正由另一Bridge使用”，保留刚建立的绑定，不再次弹码。

## 4. 最小协议与凭据

拟新增能力`binding_method=screen_confirm_v1`，AP01使用局域网HTTP完成首版配对；不运行SMP、PAKE或短认证串加密握手。固定数字不作为认证判断，不承诺抵御同网段主动攻击或窃听。保留每个设备/Bridge关系独立的普通token检查，避免其他Bridge误调用已绑定设备；OTA仍需凭据与明确升级操作，不能用显示码直接授权。

不改Note4的“经绑定加密BLE取得token”入口；这是AP01的新引导路径。AP01业务入口、claim和OTA的token都要解析到同一个已绑定principal，不能共享一个全局token却仅信任请求中自报的bridge_id。适配层可复用现有HTTP请求结构，但必须显式按能力选择验证方式，不能伪造`peerBonded`/`peerEncrypted`。

建议接口：

| 接口 | 合同 |
|---|---|
| `GET /api/pairing/info` | 最小型号、完整Wi-Fi MAC、boot_id、pairing_revision、绑定方式、是否可发起及原因；不返回token或完整绑定列表 |
| `POST /api/pairing` | 请求字段：预期MAC、boot_id、pairing_revision、request_id、完整bridge_id、名称、display_code、候选binding_token及需要的回连host/port；返回`202 pending_display`或结构化拒绝 |
| `GET /api/pairing/{request_id}` | 以本次候选binding_token查询；状态为`pending_display / awaiting_confirmation / approved / cancelled / expired / rejected`；仅approved且读回成功才可标绑定完成 |
| `DELETE /api/pairing/{request_id}` | 本次候选凭据取消待确认；不能删除已经建立的binding |
| `POST /claim` | 正式绑定凭据映射到principal，再走共享owner决策；body身份必须相等，保留租约/冲突语义 |

所有错误返回`result/error/stage/request_id`及可操作提示；HTTP单次超时建议5秒，配对总等待120秒。UI投递失败明确`display_unavailable`，不得让用户在没看见数字时完成绑定；已投递但未得到显示确认时，以截止时间结束，不标成功。

Bridge为每个设备生成并保存独立候选binding_token（16个随机字节，以32位hex传输），作为绑定后的长期凭据；设备收到时只保存为RAM候选，旋钮确认且落盘成功后才授权。候选状态下该凭据只能查询/取消自己的配对事务，不能读业务、claim或OTA。设备不在结果或日志里回显凭据，Bridge也不复用全局应用服务token。无需另外实现一次“服务端发token但响应丢失”的领取协议。

`request_id`、完整身份和候选凭据标识同一事务，重复请求字段不一致返回`request_conflict`。`boot_id + pairing_revision`处理旧请求迟到：开始时固定代次，终止/成功/owner抢先取得占用后递增代次，重传不能重新弹出已经关闭的请求；Bridge不自动读取新代次换ID重试。旋钮事件也携带当前UI请求代次，旧事件不能批准新请求。

设备在每条binding中保存最后一次成功的request_id；响应丢失、Bridge或设备重启后，可用原凭据核对该记录。查询确认已保存则完成；不能确认时显示`结果未知`，保留原请求和凭据，不自动建立第二个绑定。未确认的请求跨设备重启失效。已绑定但Bridge遗失凭据时，显示“需要重新确认”，必须由用户发起修复；设备空闲后再按旋钮，只替换这一条凭据和事务namespace，不影响其他Bridge。

## 5. 多对多存储与解除绑定

设备端一张binding表，逻辑字段为完整bridge_id、显示名称/固定码、binding_token、事务namespace、last_pair_request_id，以及现有传输确需的回连host/port。设备自身Wi-Fi MAC只存一份；不保存按IP区分的重复绑定，不长期保存每次重连会话。Bridge按稳定安装/实例身份与设备MAC保存凭据；改名称、改IP不创建新身份。

binding按实际条目序列化，包含显式magic/version、总长度、实际数量、记录长度、字段长度及CRC；先校验上限和格式再分配。完整bridge_id须原样比较，不能直接使用现有`v2PrepareClaim`的32字符裁剪结果代替原身份；AP01入口应明确校验长度，并将完整ID交给owner决策。

仅绑定、修复、删除时写持久表，不因60秒续约或状态查询重写。采用当前文件系统实际支持的原子替换与读回流程；同卷临时文件仅用于提交，不是ROM/App fallback。掉电后必须只有旧完整表或新完整表；损坏记录返回storage错误，不当作无绑定重新开放授权。这里的断电原子性要在AP01实际文件系统验收，不能以宿主rename成功代替。

AP01“已绑定Bridge”菜单可旋钮选择删除一项；若该项是owner，同时清空该owner，并使该principal的会话失效。删除A不影响B；恢复出厂/明确清空才删除全部。Bridge端仅移除本地设备不能声称设备端已解绑；设备端不存在该记录时，旧凭据明确401，不自动弹码修复。

本轮只有设计，没有新增设备运行分配。首版预算边界为8条持久记录、1个RAM候选、1条待显示消息，不新增整屏帧缓冲；实施时按最终格式提供0/1/4/8条实际持久字节、原子写峰值RAM及匹配ROM调用栈。不能把当前BRS2或历史BLE开销当成AP01的实测预算。

## 6. 两个进程的归属

| 部分 | 职责 |
|---|---|
| 常规通信/绘图进程 | 配对HTTP入口、正常claim与业务通信、投递配对画面和接收旋钮事件；网络回调不直接操作原厂UI |
| OTA进程 | OTA有界接收、校验、安装与事务查询；直接验证已经保存的binding，不依赖业务进程在线 |
| 稳定底座的共享逻辑/存储 | binding表、owner仲裁、OTA维护状态及互斥访问；不是新增第三个进程 |

业务进程停止时不能开始新的屏幕绑定，已建立的授权仍可用于OTA。OTA执行期间进入维护状态，拒绝新配对及其他principal抢占；已授权更新按其自身有界事务生命周期继续，不能用“业务进程没续约”使安装中途换人。维护状态要能从OTA结束/明确失败或重启后事务恢复中正确退出，不留永久占用。

原厂米家蓝牙任务及配网保留。0031无fallback的条件不变；两个执行单元是否具备地址空间隔离仍待验证，不作为本设计的恢复保证。

## 7. 实施顺序与验收边界

1. 先核实0031旋钮短按/释放/旋转回调、UI消息投递、常驻任务和HTTP服务入口；实现可取消的配对覆盖层。这些是新的主要逆向入口，SMP不再是前置条件。
2. 实现AP01 binding持久表、单请求状态机、claim仲裁与token映射；Bridge新增能力路由、固定码、按MAC保存待确认事务。接口与UI共用application service。
3. Fake/宿主验证后，再生成明确指纹候选并开展实机核对；本设计不代表已可刷入。

验收至少覆盖：首次同码确认；不按按钮不授权；遗留/重复按钮不确认别的请求；同ID重试不重绘；不同请求不替换；连续续约时无弹窗；最后一次续约300秒后可匹配；已绑定重连不弹码；新claim与旋钮并发的唯一结果；A/B多对多和同码不串身份；只解绑/修复一条；确认前后的网络丢包与断电；存储损坏/容量满；错误MAC；OTA维护阻止配对且业务停止后OTA可继续认证。

现有代码依据：`src/owner_store.cpp`（显式续约、业务touch不延长）、`bridge/crates/app/src/main.rs::device_claim_renew_due`（60秒）、`src/bridge_store.cpp`（端点表8条上限与principal/token映射）。这些用于复用语义，不代表AP01已有对应实现。
