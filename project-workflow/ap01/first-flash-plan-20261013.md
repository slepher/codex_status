# AP01 0031 自定义 App 变体：首次刷入与更新方案

2026-10-13。状态：最小XIP App候选已构建并离线验证，未刷入；[实现验收](app-implementation-20261013.md)。归主项目 [C9](../../docs/roadmap/backlog.md#c9-取消项目自管ab动态容量与内置更新界面)。目标为**0031自定义App变体**；0041仅供对照。设备仍运行`1.02_0031`仅来自用户报告，未做本轮运行回读。已有准备见[资料索引](preparation-index-20261013.md)，接续原[0031接入设计](design.md)。

## 1. 决策与执行边界

目标结构为 **0031原厂系统/驱动/米家配网＋稳定App加载/更新底座＋本项目Bridge App**。首次通过0031原厂OTA刷入该底座和最小App的完整ROM候选，随后在同一0031底座上接入完整Bridge业务、验证独立App更新。原生ROM双槽保留，项目App/Bundle单份。上游hack ROM的接口包装与制作工具作为参考，不把其图片看板当成本项目App。

安装规则由当前运行的更新器执行。0031没有0041新增的`signed_file=false`立即拒绝分支，且上游作者报告过0031修改版安装，所以保留0031作为系统基线和首次OTA入口。已完成的[0041签名对照](knowledge/0041签名与Bridge接口分析.md)用于解释版本限制，不增加0041迁移任务。

稳定底座负责认证控制、包验证、App装载、维护界面和失败恢复，App负责Bridge业务及绘制。沿用既有版本化C接口与单份更新设计，优先验证可返回的小模块及健康回执，再接完整App。原厂MiIO OTA保留作完整底座更新/在线回刷入口；独立App更新经本项目身份/token约束的服务，不需要修改0031的既有验签准入规则。

本轮已按用户后续授权生成最小XIP ABI诊断ROM并完成离线测试；无账号缓存读取、设备查询/RPC、固件服务器、Bridge部署、刷机或提交。候选尚无认证维护/完整Bridge/独立App OTA，后续实机按阶段执行，不能因本文含参数自动安装。

## 4. 首次OTA传输与安装设计

依据固定上游版本`3bd98a8ca4fb35a9f8869121b13961d405b16dff`的 [通信/更新实测](https://github.com/andy-JustSayWhen/cuktech-ap01-firmware-tools/blob/3bd98a8ca4fb35a9f8869121b13961d405b16dff/knowledge/AP01-%E5%AE%98%E6%96%B9%E5%9B%BA%E4%BB%B6%E5%88%86%E6%9E%90/%E9%80%9A%E4%BF%A1%E3%80%81%E5%AD%98%E5%82%A8%E3%80%81%E6%9B%B4%E6%96%B0%E4%B8%8E%E6%81%A2%E5%A4%8D.md#21-miioota-%E7%AB%AF%E5%88%B0%E7%AB%AF%E8%A1%8C%E4%B8%BA2026-08-19-%E5%AE%9E%E6%B5%8B)及`features/firmware_installation/install.py`、`tools/ota_https_serve.py`；2026-10-13在线再次读取前者。以下是作者实测和本轮设计，尚未在用户设备执行。

### 4.1 临时文件服务

- 优先同一局域网HTTPS：`https://<服务器实际IPv4>/miio_fw/<已冻结文件名>`。作者实测云端检查路径首段，普通FDS上传桶曾被拒；首次方案不依赖额外米家网关或公网存储。
- 服务使用HTTP/1.1、固定Content-Length、application/octet-stream，按4 KiB应用块写入TLS流；应用write大小不保证实际TLS record边界。上游报告默认16 KiB记录及所用AES256协商曾失败，先采用其测试过的AES128 cipher配置；拟选TLS1.2，兼容性待测。记录实际协商版本/cipher，并用抓包或等价证据核对记录长度，不从服务器配置直接推断。
- 若使用临时自签证书，此次0031安装请求明确`cert_verify=optional`。这是TLS策略，与固件`signed_file`验签不同；不修改日常Bridge TLS或鉴权规则。
- 成品文件先回读逐字节/SHA256一致，再发送安装。服务器只提供选定文件，不提供目录浏览；绑定确认的LAN地址，必要防火墙规则限定AP01来源，检查443占用，不抢其他服务或扩大到公网。
- 证书、私钥、地址、账号、设备身份及原始响应放Git忽略的artifacts。记录阶段/数量/文件哈希，不完整打印请求头、账号或token。任务结束关闭本次服务并撤销本次新增规则。

上游服务器会在第三方`tools/`生成证书且完整记录请求头；安装器默认选择唯一AP01，简单dispatch脚本只打印RPC后即退出。这些都需要在本仓库包装或重新实现，不能直接当最终执行工具。Windows DPAPI缓存保持现位置，不为兼容env-file接口导出明文凭据。

### 4.2 一次下发的参数草案

```json
{
  "app_url": "https://<LAN IPv4>/miio_fw/<candidate.bin>",
  "file_md5": "<冻结成品的实际MD5>",
  "signed_file": false,
  "original_length": "<冻结成品字节数；实际JSON使用整数>",
  "app_force": 1,
  "cert_verify": "optional"
}
```

该草案仅用于已核实0031的首次网络OTA；合法受信任服务器不需要为自签证书采用optional。`app_force`取自上游同版本修改包实测，不把它视为降级或0041签名绕过。`proc/mode/install`未被上游0031参数解析识别，不依赖其形成“仅下载不写入”阶段；下载可能已写待更新槽，收满前也不能承诺纯RAM操作。`app_hostip`强制引流曾无效，不使用DNS劫持替代实际可达URL。

### 4.3 状态、时限与验收

拟定执行器具有preflight、served、dispatched、observing、verified、rejected、unknown终态。安装前保存life及OTA错误时间基线；每2–5秒有界查询`miIO.get_ota_state/progress/info`，默认总观察6分钟，明确拒绝直接终止。发送前将任务ID、DID、成品指纹和状态私有落盘，再**仅下发一次**；响应丢失/超时/进程重启只续查该任务，不自动再次miIO.ota。

云端`code=0/ok`仅为受理；服务发送完只为传输；progress=100/101或idle单独都不能证明新ROM。P2/P3完成需本次下载/安装证据、相对安装前life重新计数或等价启动证据、重新上线、无本次新错误以及构建标识/功能核验。life是运行时间，下降只支持重启判断，不能单独证明装入了指定哈希。P4建立真实回读接口后才增加认证运行哈希核验。

未见下载先查URL转发/网络；TLS失败查证书/记录长度；明确版本/签名/CRC拒绝标注失败阶段；下载后长期离线标为结果未知或启动待恢复，不标成功，不循环重发。初版不把只读查询超时变成无限等待。

## 5. 0031稳定底座与后续应用更新

原厂完整ROM OTA继续使用原生双槽，是否自动回退另验。本项目应用和Bundle遵循 [单份更新设计](../single-copy-updates/design.md)：运行期间将包下载到实时足够的空闲空间，传完核对长度/CRC/格式，再切内置维护界面并停止应用、覆盖单份内容；覆盖失败留维护界面，身份/绑定/恢复入口保留。临时文件不等于应用A/B，不占原生备用固件槽存Bundle。

稳定底座持有更新入口、认证、文件写入和维护界面。独立可执行应用加载、重定位、可执行内存和退出/资源释放尚未证实；若无法落实，先以完整ROM迭代，不能把GIF下载或/resource文件上传当作已部署代码。CSZ1是统一压缩格式候选，但AP01解压ABI未验，首次原厂ROM OTA仍传其兼容的原始BFNP文件，不擅自改成压缩包。

0031底座后续完整ROM更新须分开检验：受控入口权限 → 型号/布局/长度/完整性 → 目标槽写入和读回 → 切槽提交 → 重启运行核验。App-only更新则使用文件装载/单份覆盖路径，不切原生ROM槽。原厂Boot2/eFuse信任约束仍适用，新增应用层入口不会自动解除它们。恢复服务不得依赖被覆盖的Bundle/应用；具体接口随当前Bridge合同实现，不先发明免token更新端口。

## 6. 恢复等级与失效处理

| 等级 | 可做什么 | 当前状态与缺口 |
| --- | --- | --- |
| R0 原厂OTA回刷 | 应用仍可联网/收MiIO命令时回到已冻结0031原件 | 作者报告原厂0031同版本重装和修改版安装；修改版到原厂的同机回刷未被这些记录证明。用户设备未验，也不保证0041降级 |
| R1 原生槽恢复 | Boot2选择旧槽，或可操作入口切回 | 双槽/表选择代码已见；自动回退、次数、触发条件和入口未验 |
| R2 UART/USB ISP | 应用不运行时识别芯片并恢复确认的区域 | 芯片族支持，AP01引脚/电平/启动选择/USB数据线路、权限/eFuse未知；不能因背后Type-C直接视为成立 |
| R3 调试接口恢复 | 经JTAG等已确认且允许的调试接口读取/恢复 | AP01接线、调试权限及安全限制未验，不将通用芯片支持视为可用 |
| R4 外部Flash恢复 | 恢复同机启动/分区/应用内容 | 未核实实体Flash、读取/供电方式及加密/安全约束 |

独立恢复调查顺序：确认板级线路与接口 → 下载态只读识别和安全配置 → 同机Flash/Boot2/两份分区表/设备专属数据两次一致读取并保存指纹 → 依据真实布局制定选择性恢复 → 可控的恢复及启动验证。两次读取一致只证明备份稳定；原件BFNP不替代同机全备份。拆机/接线/写回属于后续实际操作，本文没有给未知焊盘指定GPIO或芯片族默认烧录偏移。

R0–R4沿用上游恢复分类；R2中的USB分支仅为待板级核验的ROM下载候选，不证明后置Type-C支持ISP。若OTA明确拒绝而旧系统在线，保留现场并修正明确原因；若安装结果未知，先查询原任务和life/错误，不重新下发；若新系统在线但功能异常，走已验证R0；若系统不在线，只有已验证R1/R2/R3/R4才称可恢复。备用槽会被下一次更新使用，不能当永久原件备份。
