## dump定位与边界

官方esp-coredump 1.17.2 + 本机Xtensa GDB离线解码成功。崩溃任务nimble_host；EXCCAUSE=0x14 InstFetchProhibited，PC/EXCVADDR=0。默认GDB回溯因PC=0未恢复正常窗口地址，不能把其输出的0x0200474a当真实flash地址。

寄存器a8=0x820169fc按Xtensa窗口返回地址恢复为0x420169fc；匹配ELF反汇编显示前条指令0x420169f9是nimble_port_run内的callx8，读取ev+4（回调fn）后间接调用。a10/a7=0x3fca9558，经ELF符号与DWARF结构核对正是 `&ble_hs_timer.ev`（timer=0x3fca9550，event偏移8）。因此本次直接故障是主机timer事件的空回调被执行，而非USB控制线复位。

同一dump的loopTask明确处于：loop → v2RendezvousTick → bleOff → bleDeinit → NimBLEDevice::deinit → nimble_port_stop → ble_hs_stop → ble_gap_preempt → HCI广播停止。nimble_host栈used/free=656/7528，loopTask=1696/10588，不支持把此次直接故障归为已捕获的栈耗尽。

库源码显示：ble_hs_stop_begin设置STOPPING后调用ble_hs_timer_resched；ble_hs_timer_reset在host未启用时stop/deinit该timer；npl_freertos_callout_deinit删除timer后memset整个callout（包括ev.fn），未在该函数中清除已经入队的事件；nimble_port_run无条件ev->fn(ev)。这与转储的timer事件地址/空fn/并发关闭状态高度吻合，指向关闭时已入队timer事件被清空后继续执行的竞态。**精确清空者/事件入队交错尚未用定向生产调度复现；没有将源码解释冒充修复验收。** Wi-Fi snapshot恰好在附近不是其导致panic的证据。

## 串口对照

| 操作（各15s） | 观测 |
|---|---|
| os.open/read/close，无modem ioctl | boot_id保持，uptime连续，无ROM reset |
| pyserial跳过DTR/RTS更新、保留接收缓冲，open后清HUPCL | boot_id保持，uptime连续，无ROM reset |
| 普通pyserial open前dtr=false/rts=false | 立即ROM USB_UART_CHIP_RESET，boot_id改变，uptime重起 |
| 跳过modem更新后单独写DTR=false | 再次立即USB_UART_CHIP_RESET |
| 随后单独写RTS=false | boot_id保持，无第二次复位 |

对照时间20:36:28–20:38:39。结果限同一设备/主机/起始控制线状态；没有断言所有OS open或所有RTS写均不复位。pyserial POSIX open会按顺序发modem ioctl；false/false只是期望最终值，不能保证过程中不触发原生USB硬件复位。esptool复位是刻意的ROM进入/退出流程；普通监听可以避开该行为。

监听recipe（只作诊断，不改控制线；先枚举并核对MAC）：

```python
class PassiveSerial(serial.Serial):
    def _update_dtr_state(self): pass
    def _update_rts_state(self): pass
    def _reset_input_buffer(self): pass

port = PassiveSerial(port=None, baudrate=115200, timeout=0.1)
port.port = verified_port
port.open()
attrs = termios.tcgetattr(port.fileno())
attrs[2] &= ~termios.HUPCL
termios.tcsetattr(port.fileno(), termios.TCSANOW, attrs)
# 保存read()原文；finally close；前/中/后读取认证boot_id/uptime/reset_reason。
```
