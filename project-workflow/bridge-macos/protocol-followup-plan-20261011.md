## Review：结项闸门

### 人工唤醒准入缺口（2026-10-11，实机反馈后重开）

- 用户确认两次 BOOT 后 Wi-Fi 均为空，第一次约 5 秒后睡眠，按前已有睡眠标记。标记不能证明按下瞬间 CPU 的实际睡眠状态；第一次事件与日志时间尚未完整对齐。
- 已确认代码缺口：`rendezvous.rs` 的 `needs_http` 只计待办/诊断，不计人工唤醒；随后才读取 `provisional_remaining_s`。service 虽记住 `manual_until` 并保留 Light，发给固件的 `need_http` 仍可为 false。因此“Light 剩余约 295 秒、无待办、不开 Wi-Fi”能解释实现，但不满足用户明确的人工唤醒联网语义，不能作为正常行为验收。
- 修复规划：区分人工唤醒的联网意图与定时 BLE 交汇的工作准入。人工窗口内无待办也应有界尝试联网；timer 无任务仍保持 BLE-only。首个正式 Plan 后 provisional 清零不得丢失人工意图，也不得每轮重新授予 300 秒；明确显式关闭、失败和窗口到期的退出。Wi-Fi 元数据继续报告真实 idle/connecting/connected/off，由模板决定显示，不伪造 ON。
- 必补生产路径回归：人工无待办、首个 Plan 后再次会合、timer 无待办、联网失败、窗口到期/显式结束及重复消息不续期。另查第一次 5 秒入睡的物理按键/唤醒原因/Plan 时间线，不将第二次准入缺口直接当作第一次根因。
- 文档也有冲突：generic-display-platform-design §7 写正式 Plan 可缩短 provisional，紧接着又规定人工窗口取大；其 BOOT 示例仍把 300 秒缩成 63 秒。实施时应按已确认的人工窗口规则统一说明与测试。

状态：已定位准入缺口并修正调查结论；此补充未修改或部署程序，前述 316 项测试不能覆盖这一缺失场景。
