# 协议收敛实施计划

2026-10-19 用户授权文档化并开始重构。依据 [核验报告](protocol-review-validation-20261019.md)，唯一待办归 B6/C8。

## 范围与发布合同

- 协议变动必须覆盖 Bridge、Note4（zectrix-note4-b）、1.54（esp32-s3-epaper-154g）、Fake ROM、AP01。Note4/1.54 共用源码不免除双目标构建和编码验证；不涉及 gray4/btpm。
- 不实现旧版兼容、双协议或猜测降级。最终协议不匹配明确失败；持久业务身份、未知提交证据及回执围栏不能作为“旧兼容”删除。
- 用户允许：因协议升级使 Bridge OTA 协议通道失效时直接走裸 OTA。裸 OTA 是已有受鉴权的固件更新入口，不是免 token 写入；先核对登记 MAC、真实设备/目标、镜像 marker/大小/SHA256，更新后独立核验运行镜像。不得因此擦 NVS、dump、分区或强制 claim。
- 分批内部重构可先保持 wire 不变；任何 wire 切换必须先完成四端合同/测试/产物清单。部署与源码完成分开记录，不把当前设备仍运行旧软件当成兼容要求。
- AP01 覆盖对象是本仓库 `ports/ap01/` 的当前应用及共享协议核心、Bridge客户端和device-sim，不是原厂固件逆向仓库。用户已纠正这两者的区别；原厂仓库路径缺失不是本轮源码重构阻塞。当前应用通过XIP链接后打包完整0041 ROM，可修改源码并重建；尚不能据此宣称支持应用代码独立更新，该发布耦合记入C9。

## 切片

1. R1：已知 MAC 入口统一设备→BLE 顺序和有界等待；自动会合拆开发现/连接，忙设备不得占全局 BLE 等 HTTP。
2. R2：有限执行终点与历史结果/回执收尾分离；原 ID、身份、未知事实保留，不复活旧写。明确永久 unknown 与容量失败的用户恢复合同。
3. R3：扩展已有 OperationReply，AcceptedPending 正常返回；本地意图、退避、观察、联系证据与共享 UI/MCP 投影分离。
4. R4：RendezvousContext 替换 13 个私有 JSON 字段，复用现有 Wi-Fi 执行核心。
5. R5：异步 HTTP 及 session 锁迁移；之后独立收敛 CommandContext 和 wire 字段，按四端矩阵交付。

## 验收与迁移

每片先针对真实边界做回归，依赖面变化后再扩大测试。R1 验证 A 设备占用时 B 可取得 BLE、全局占用时本设备等待有总截止、取消不漏锁、worker 在途许可继续有效。R2 验证连续丢 ACK/重启/身份变化、8 回执及32 Job容量、停止执行后原 ID 收尾。后续详见核验报告各 R 验收。

Bridge 持久格式变化需显式迁移和冻结备份/回滚限制。设备格式与协议变化列空/单/典型/上限的存储/RAM/栈预算，匹配 ELF 门禁。UI 变动运行项目规定的 Node/WK 与窄宽截图。RF、Flash掉电、实体屏幕和原生 BLE 取消不由 Fake 代验。未经要求不提交。
