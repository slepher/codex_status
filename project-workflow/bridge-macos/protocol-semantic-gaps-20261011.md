# 协议行为缺口审核与失联恢复入口

后续结论：用户已明确窗口开关、HTTP 优先及断网 BLE 汇报合同，候选实现与证据见[BOOT 联网实施](boot-network-20261011.md)。下文保留调查时点，旧“Light 断网仍禁 BLE”不再适用；G2 按键与睡眠竞态及物理验收仍未关闭。

日期：2026-10-11。范围：人工操作、BLE 交汇、联网与休眠衔接；关联 backlog A9/B6/C8。只读审核及文档记录，未改变运行设备。本文建议不是已批准的新协议，也不把源码现状当作产品要求。

## 判据与结论修正

“没有 HTTP 待办所以人工唤醒不开 Wi-Fi”是实现解释，不是完整的协议依据。总设计 §7 的 BOOT 流程画出了 Wi-Fi 连接，但场景合同 §1 又将 HTTP 准入限制为必要业务；统一在线设计 §2.2 只说按当前网络能力提供 HTTP。缺的是这些条款之间可执行、可验收的边界。用户明确人工唤醒按常理应联网；先前报告将它直接表述为违反既有完整合同，表述过强。

## 应另列的文档冲突，不冒充纯遗漏

### G7 / P1：Light 的联系载体与断网退出（用户本轮已确认核心规则）

Light 设备主动 HTTP 联系 Bridge，普通 BLE 全程关闭，只有用户 BOOT 主动开启恢复窗口例外。此前“合法 BLE 机会”没有按设备电源阶段限定，允许实现把 Light 无 Wi-Fi 当作下一轮 BLE 条件。缺少的后续条款是 HTTP 联系节奏/内容/失败预算、Light 断网重连及退出条件；不能自行解释为普通 BLE 回退。正式修订见通信场景 §1。

源码线索：application.cpp 的无 wifiUp 且 nextBleContactMs 到期分支调用 v2RendezvousBegin，没有排除 Light；power.cpp 的插电/电量分支及 radio.cpp 的 startNormalMode 仍有自动 enterBleOn(false) 入口，radio.cpp 的 serviceBleSession 仍保留 USB 普通 BLE 常驻策略。需按新约束逐入口核对，不能只关闭当前一次连接。与新规则相违是当前明确可检查的实现差异，不再属于完全未定的行为。

- 总设计 §7 同时存在“正式 Plan 可缩短 provisional”与“物理窗口取大，只显式入口提前结束”；§12 的 BOOT 示例仍把 300 秒缩到 63 秒。应先统一权威语义。
- power-state §3 仍写仅失联/AP才主动 deep、深睡醒来两种无线一同初始化；总设计 §7 已定义 timer BLE-only 和正常 Light 到期 deep。这是残留条款冲突。
- 本轮没有把丢 ACK 换事务、OTA 上传等于成功、读取自动续期列为缺口：现有合同已明确禁止。诊断在 Light 到期后的有进展收尾也已有专门定义，不能误称未规定。
- 已有 Bridge manual_until 字段带序列化；仅凭设备首个 Plan 后 provisional 清零，不能断言 Bridge 重启必丢人工窗口。

- 软件恢复路线：下一合法 BLE 机会可用 status/原事务查询；显式 Wi-Fi 完整读取或已授权 OTA 任务可使 HTTP 工作进入准入，经过网络准备与认证验证后再操作。仅下发 Light 不保证开网，正是 G1 暴露的区分。此处只核对代码路径，未额外排任务或承诺 RF 成功。
- 有线通信路线：USB 数据线接电脑后枚举 VID/PID/serial 并核对设备。应用正常运行时 Serial CLI 有 status/log/pmstats，pair 可开启恢复窗口；这些入口依赖主循环运行，不是 ROM 下载器的业务命令。Windows 监听须遵守不改 DCB/DTR/RTS 的操作细则。
- 有线烧录路线：原生 USB-Serial-JTAG 的 ROM 下载入口不依赖应用 Wi-Fi/BLE；连接后核对真实 MAC/分区与 Note4 ROM，必要时进入下载模式。刷写后做读回/运行身份核验。当前没有连接，不能宣称 ROM 入口已在本次故障现场验证。不得全片擦除；已有 OTA 后 USB 写入还须按实际分区/otadata 处理启动槽，不能直接假定写 ota_0 就会启动。
