## 结论与边界

根因未定。用户发现画面停在用量「80多」、旋钮无响应，确认发生在用量重置之前；发现后自行拔电重启，重启后正常。本轮取得的设备状态和 RAM 日志均在拔电之后，不能证明死机时整机、LVGL 或输入任务的运行状态，也没有旧任务栈可解码。没有将用量重置认定为触发因素。

本次只读调查，无刷机、切槽、重启 Bridge、设备配置修改或业务数据注入；调查工具未主动重启设备。没有访问串口（枚举只有系统蓝牙端口）。现场已恢复，未获得可重复触发的反馈环，因此没有猜改代码或宣称修复。

## 源码核对与不能成立的推断

- `ports/ap01/business.cpp` 的 Data 分支先由 `v2DecideData` 接收/去重，firstApplied 才调用 render；重试已接收 seq 会得到 applied/unchanged。故 unchanged 既不是绘制成功，也不是「用量没有变化」的证明。
- `src/v2_data_command.cpp` 区分 firstApplied 和 unchanged；`ports/ap01/native_0041.cpp` 的 `imageDrawn` 才提交绘制代次。Bridge 普通日志的 ACK 未保存当时的 frame_generation、UI heartbeat、display_reason 或任务栈。
- 本次快照摘要只保存 CRC、字段数量和 missing 清单，不包含具体剩余额度或 resetsAt 值。5h/月度字段在异常前后均为 missing，未观察到这两组字段从有到无的切换；周窗口重置时间、80多所指字段以及变更时刻未知。不能从 CRC 反推用量重置。
- 拔电后的 RAM 日志/输入 trace 只能验证恢复后的当前运行；旧码失效造成的 401 已用用户提供的当前码解决，不能当设备死机证据。

## 17:18 补查：原厂 crash 分区已单独保存

用户继续要求检查并单独保存 dump。原始 0041 ROM 中发现 `BFLB COREDUMP v0.0.1`、`/dev/crash`、`coredump_flag` 和 crash partition 字符串，说明原厂含相关机制，不能直接认定 AP01 不支持 crashdump。现有维护文件接口仅允许 `/data/`、`/resource/` 与 `/dev/ramlog`，因此经其已有只读 physical Flash 接口导出，不更改路径白名单。

先读取实际 `0xe000`/`0xf000` 两份分区表，均校验头 CRC/条目 CRC，修订44/45；新表 FW active1，与现部署一致。两表均登记 `Crash` 类型5，起点 `0x720000`、长度 `0xc000`（49152 B），与 FW/Data/bt 分开。

已逐块读取全部 Crash 分区，核对同 MAC、同 boot 和每块 CRC，结束复核 boot 未变。独立原文 `artifacts/ap01-freeze-20261028/crash-partition-0x720000-0xc000.bin`，SHA256 `2aae7dc846aaf25f1cadf55f1666862046c6db9d65d84bdc07fa039dac405606`；旁有读取时间/边界/校验元数据及实际分区表。**49152 B 全为 0，没有可识别的 crashdump 头、寄存器或任务栈可供解码**。这证明当前读取结果没有可用 dump，不能证明此前未发生 panic；是否原厂未触发保存、启动/上报流程曾清理或这次只是卡死，均未确定。只读导出未清除设备内容、未整槽导出、未复位/刷机；原文含潜在敏感信息，留私有 artifacts。
